02Thread em dois minutos

Um processo é um programa rodando: tem a memória dele, os arquivos abertos dele. Uma thread é uma linha de execução dentro do processo. Todo programa começa com uma thread (a principal), e pode criar outras.

Pense numa cozinha. O processo é a cozinha inteira: bancada, geladeira, panelas. Cada thread é um cozinheiro. Vários cozinheiros na mesma cozinha usam a mesma bancada, ou seja, as threads de um processo compartilham a mesma memória. Isso é ótimo (não precisa copiar o vetor para cada uma) e perigoso (dois cozinheiros podem mexer na mesma panela ao mesmo tempo, que é a condição de corrida).

E os fogões são as CPUs. Com 2 fogões, no máximo 2 cozinheiros cozinham de verdade ao mesmo tempo. Se você chamar 8 cozinheiros, 6 ficam esperando a vez. Guarde essa imagem: ela explica a seção 11.

No código: a biblioteca é a pthreads (POSIX threads), incluída com #include <pthread.h> e compilada com -pthread.

03O Quick Sort

A ideia é dividir para conquistar:

  1. Escolha um número do vetor, o pivô.
  2. Reorganize o vetor: menores (ou iguais) que o pivô à esquerda, maiores (ou iguais) à direita. Isso é particionar.
  3. Repita a mesma coisa em cada lado, até sobrar pedaço de 1 elemento.

Avance passo a passo para ver o particionamento do nosso código (Hoare com mediana de três). O i anda da esquerda, o j da direita; quando os dois param num número do lado errado, eles trocam.

dois detalhes do nosso código

Mediana de três: em vez de pegar sempre o primeiro número como pivô, olhamos o primeiro, o do meio e o último e usamos o do meio dos três. Isso evita o pior caso (pivô sendo o menor de todos, deixando um lado vazio).

Insertion sort nos pedaços pequenos: com até 16 elementos, um algoritmo simples é mais rápido que continuar dividindo.

No código: comum.h — particionar() e quicksort_seq(). As duas versões usam essas mesmas funções.

04Por que dá para paralelizar

Repare no fim da demo anterior: depois de particionar, nenhum número da esquerda vai para a direita, nem o contrário. Os dois lados são independentes. Então dá para entregar cada lado para uma thread diferente.

Na demo abaixo, cada faixa é um pedaço do vetor e a cor diz qual thread trabalha nele. Escolha o número de threads e clique em animar.

como o vetor é repartido entre as threads

Três coisas para notar:

  • Nível 0 é só da T1. A primeira partição percorre o vetor inteiro com uma thread só, antes de existir qualquer divisão. Essa parte não paraleliza. É ela que impede o ganho de chegar a 2× com 2 threads (Amdahl).
  • Orçamento de threads. Cada chamada recebe quantas threads pode usar e reparte entre os lados pelo tamanho. Pedindo 4, nunca passam de 4.
  • A carga não fica igual. As barras do fim mostram quanto cada thread ordenou: o pivô não divide exatamente ao meio.

A demo usa um vetor de 2.000 números e limite de 128 para caber na tela. O programa de verdade usa limite de 4.096 com vetores de até 400 mil números; a lógica é a mesma.

05pthread_create e pthread_join

Só duas funções da biblioteca fazem todo o trabalho:

FunçãoO que faz
pthread_createcria uma thread nova e manda ela executar uma função
pthread_joinespera uma thread terminar

linha do tempo de uma divisão

Um detalhe de C: a função que a thread executa precisa ter o formato void *funcao(void *arg), recebendo um único ponteiro. Como precisamos passar 4 coisas (vetor, começo, fim, orçamento), empacotamos tudo numa struct Tarefa e passamos o endereço dela. A rotina_thread só desempacota e chama quicksort_par.

typedef struct { int *v; long lo, hi; int orcamento; } Tarefa;

static void *rotina_thread(void *arg) {
    Tarefa *t = (Tarefa *)arg;
    quicksort_par(t->v, t->lo, t->hi, t->orcamento);
    return NULL;
}
por que a struct pode ficar na pilha

A Tarefa esq é uma variável local. Isso só é seguro porque a função espera a thread terminar (pthread_join) antes de retornar. Se retornasse antes, a nova thread estaria lendo memória que já não existe.

06Condição de corrida e mutex

Condição de corrida é quando duas threads mexem no mesmo dado ao mesmo tempo e o resultado depende de quem chega primeiro. O exemplo clássico é contador++, que parece uma operação só mas são três: ler, somar, gravar. Avance a tabela:

duas threads fazendo contador++

O mutex (trava) resolve isso: só uma thread por vez entra no trecho que mexe no contador. Mas trava tem custo, e as threads ficam esperando umas às outras.

por que o nosso código não precisa de mutex

Depois da partição, cada thread escreve só na sua faixa do vetor: v[lo..p] para uma, v[p+1..hi] para a outra. As faixas não se sobrepõem, então não existe dado escrito por duas threads ao mesmo tempo. A única sincronização necessária é o pthread_join, para saber quando a outra terminou.

E o main?

O main lê o número de threads da linha de comando (um número ou max, que usa sysconf(_SC_NPROCESSORS_ONLN) para descobrir quantas CPUs a máquina tem), lê o arquivo, e só então liga o cronômetro em volta da ordenação:

double t0 = agora_segundos();
quicksort_par(v, 0, n - 1, threads);     /* <-- região medida */
double t1 = agora_segundos();

Depois confere se o vetor está em ordem e se a soma dos números é a mesma de antes, e imprime uma linha: pthreads,2,400000,0.018…,1,1.

A conta com os nossos números

Entrada grande, 2 threads: Tseq = 32,85 ms e T2 = 18,01 ms.

S = 32,85 / 18,01 = 1,82   → 1,82 vezes mais rápido
E = 1,82 / 2      = 0,91   → 91% do ideal

Lei de Amdahl: o teto do ganho

Se uma fração s do trabalho só pode rodar numa thread, o speedup com p threads é no máximo 1 / (s + (1 − s) / p). Mexa nos controles:

Lei de Amdahl

No nosso Quick Sort, a parte que só roda numa thread é o primeiro particionamento (o nível 0 da seção 4).

curiosidade (conta, não medição)

Se toda a perda viesse só da parte sequencial, dá para fazer a conta ao contrário: com S = 1,82 e p = 2, s = 2/1,82 − 1 ≈ 0,10, ou seja, uns 10%. Na prática parte da perda também vem do desequilíbrio do pivô e do custo de criar threads, então isso é só uma ordem de grandeza.

Como ler

  • Ganho: a paralela venceu nas três entradas, e quanto maior a entrada, maior o ganho. Em vetor pequeno o custo fixo de criar e esperar threads pesa mais.
  • Saturação: com 4 e 8 threads o ganho parou de subir: só existem 2 CPUs.
  • Piora: na entrada grande, 8 threads levaram 20,36 ms, mais que as 18,01 ms de 2 threads.
  • Um ponto fora da curva: na média com 2 threads, a 1ª repetição levou 9,1 ms, contra cerca de 5,7 ms nas outras. Isso puxa a média para cima e o desvio padrão mostra. É por isso que se repete a medição.

11Por que mais threads piorou

Volte aos cozinheiros: 2 fogões, 8 cozinheiros. Eles revezam, e cada troca de cozinheiro no fogão custa um tempinho (tirar uma panela, pôr outra). No computador isso é a troca de contexto: o sistema operacional salva o estado de uma thread e carrega o de outra. Ainda tem o custo de criar cada thread.

2 CPUs dividindo o mesmo trabalho entre k threads

Com 2 threads, cada uma fica no seu núcleo e não há troca. Com 8, o mesmo trabalho total gasta tempo extra com criação e trocas. É o que medimos: 18,0 → 20,4 ms na entrada grande.

cuidado ao explicar

A animação é um modelo didático: os tempos dela não são medidos. Os números de verdade são os da seção 10.

Numa máquina com mais núcleos (8 ou 12, por exemplo), 4 e 8 threads devem dar ganho maior. Mesmo assim, o primeiro particionamento sequencial continua limitando o teto.

13Glossário

Thread
Linha de execução dentro de um processo. As threads de um processo compartilham a memória.
pthreads
A biblioteca de threads padrão POSIX (Linux, macOS). Usada com #include <pthread.h>.
pthread_create
Cria uma thread nova e manda ela executar uma função.
pthread_join
Faz a thread atual esperar outra terminar.
Pivô
O número usado para separar menores e maiores. No nosso código, a mediana de três.
Particionar
Reorganizar o trecho em "≤ pivô" e "≥ pivô". Depois disso, os dois lados são independentes.
Condição de corrida
Resultado errado porque duas threads mexeram no mesmo dado ao mesmo tempo.
Mutex
Trava que deixa só uma thread por vez num trecho. Não precisamos porque as faixas do vetor não se sobrepõem.
Orçamento de threads
Quantas threads uma chamada ainda pode usar; é dividido entre os lados pelo tamanho.
LIMITE_PARALELO
4.096: trechos menores que isso não ganham thread nova.
Speedup
Tseq ÷ Tp. Quantas vezes ficou mais rápido.
Eficiência
Speedup ÷ p. Quanto cada thread rendeu; 1 é o ideal.
Lei de Amdahl
A parte que só roda numa thread define um teto para o ganho, por mais threads que se use.
Troca de contexto
O sistema salva uma thread e carrega outra no mesmo núcleo. Custa tempo e não produz trabalho.
CPU lógica
Cada "núcleo" que o sistema enxerga. A máquina dos testes tinha 2.
Desvio padrão
Quanto as repetições variaram em torno da média.

14Se te perguntarem

Por que não usaram mutex?

Porque cada thread escreve só na sua faixa do vetor e as faixas não se sobrepõem. Não existe dado escrito por duas threads ao mesmo tempo, então não há condição de corrida. A sincronização necessária é o pthread_join.

Por que o speedup não chegou a 2 com 2 CPUs?

O primeiro particionamento percorre o vetor inteiro com uma thread só; essa parte não paraleliza (Lei de Amdahl). E o pivô não divide exatamente ao meio, então uma thread termina antes e espera a outra.

Por que 8 threads foi mais lento que 2?

Só havia 2 CPUs. As threads extras custam para criar e passam a revezar nos mesmos núcleos (troca de contexto), sem processamento a mais.

Como vocês controlam quantas threads existem?

Com um orçamento passado na recursão e dividido entre os lados proporcionalmente ao tamanho. Quando chega a 1, a chamada segue sequencial. Nunca passam de p threads ativas.

Por que o limite de 4.096 elementos?

Para pedaços pequenos, criar uma thread custa mais que o tempo que ela economiza. Abaixo disso é mais rápido ordenar direto.

Como sabem que as duas versões dão o mesmo resultado?

Comparamos a saída byte a byte com cmp em todas as configurações e conferimos a sequencial contra o sort -n. Cada execução também confere se está em ordem e se a soma dos números não mudou.

O que exatamente foi cronometrado?

Só a chamada da ordenação, com clock_gettime(CLOCK_MONOTONIC). A leitura do arquivo e as verificações ficaram fora nas duas versões.

A versão paralela não é "outro algoritmo"?

Não. Ela usa o mesmo particionar e, nos pedaços, chama o mesmo quicksort_seq. A única diferença é que os níveis de cima da recursão são distribuídos entre threads.

Por que a struct Tarefa pode ser variável local?

Porque a função espera a thread terminar (pthread_join) antes de retornar. Enquanto a thread nova usa a struct, ela ainda existe.

E se o pthread_create falhar?

O código testa o retorno. Se falhar, a mesma thread ordena os dois lados. O programa fica mais lento, mas não quebra nem dá resultado errado.

Num computador com mais núcleos, o que mudaria?

Esperamos speedup maior com 4 e 8 threads, até o número de núcleos. O primeiro particionamento sequencial continuaria limitando o teto.
